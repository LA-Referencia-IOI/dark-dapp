# dARK 2.0

![dARK Logo](docs/figures/dARK_logo.png)

**dARK** (Decentralized Archival Resource Key) is a blockchain-based implementation of the [ARK](https://arks.org/) identifier scheme.

**dARK is public, federated digital infrastructure.** It ensures permanent, decentralized access to identifiers while preventing proprietary appropriation of the core protocol.

## Architecture Overview

dARK 2.0 uses a **two-contract modular architecture**, separating access control from data storage:

| Contract        | Role                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------- |
| `Authority.sol` | Registers organizations (Authorities), binds UUIDs to wallets, and manages NAAN permissions |
| `dARK.sol`      | Pure ARK identifier storage — delegates all permission checks to `Authority.sol`            |

```
Admin ──► register_authority ──► Authority.sol ◄── is_authorized? ◄── dARK.sol ◄── create_ark ◄── Authority Wallet
```

## Configuration

Edit `config.ini` at the component root (the file ships with the component;
there is no separate example file):

```ini
[base]
blockchain_net = dark-local        # active network section

[dark-local]
url                   = http://localhost:8545   # HTTP JSON-RPC endpoint of the target node
acoupled_setup        = True                    # True → sign with the master wallet below; False → hardcoded Besu dev-genesis account
master_wallet_address = 0x...                   # wallet of the deployer / contract admin
master_private_key    = 0x...                   # matching private key
```

Notes:

- `dARK_dapp/deploy.py` reads `url`, `acoupled_setup`, `master_wallet_address`
  and `master_private_key` (keys are case-insensitive) from the active network
  section, and also loads an optional root `.env` via python-dotenv.
- With `acoupled_setup = False`, `deploy.py` signs with the hardcoded
  Hyperledger Besu dev-genesis prefunded account instead of the configured
  master wallet.
- `chain_id` and `master_public_key` are recorded in the file for reference
  but are not read by the scripts (the chain id is taken from the node at
  runtime).

> **Important:** The account in `master_wallet_address` becomes the `admin` of the `Authority` contract. Only this account can call `register_authority`.

## Deployment

The Solidity contracts of this component (`Authority.sol`, `IAuthority.sol`, `dARK.sol`) are deployed by the [dark-deployer](../../README.md) using the deployment v3 pipeline: an operator inventory (see [examples/operator-inventory/](../../examples/operator-inventory/)) is resolved, planned, and rendered into per-machine Docker Compose bundles, then applied with `./deploy.sh install` (locally) or `prepare`/`push`/`apply` (remote hosts). During apply, the pipeline compiles `dARK_dapp/contracts` with a pinned solc-js 0.8.17 image and deploys the resulting `Authority` and `dARK` contracts through the one-shot `contracts-deploy` service; the component checkout branch (`main`) is pinned in `deployment_v3/catalog_data/dark-platform-baseline-v1.0.json`. There is no standalone docker-compose file in this component.

### Standalone development workflow

For development against a node of your own (configured in `config.ini`):

1. **Compile the contracts** (required before deploying — `deploy.py` does not compile):

   ```bash
   cd dARK_dapp
   python3 compile.py
   ```

   Artifacts (ABI + bytecode, solc 0.8.17) are saved to `dARK_dapp/compiled/`.
   `compile.py` can also run inside the `besu-compiler` Docker image built from
   `dARK_dapp/Dockerfile`.

2. **Deploy the contracts**:

   ```bash
   python3 deploy.py
   ```

   This will:

   1. Deploy `Authority.sol` (the configured master wallet becomes `admin`)
   2. Deploy `dARK.sol`, passing the `Authority` address to the constructor
   3. Save both addresses and ABIs to `dARK_dapp/deployed_contracts.ini`

## Interactive Testing (Jupyter Notebook)

The notebook `dARK_dapp/test/test-dapp.ipynb` provides a full interactive workflow:

1. **Connect** to the Besu node using the `url` from `config.ini`
2. **Load** the deployed contracts from `deployed_contracts.ini`
3. **Create** two fresh authority wallets (`Account.create()`)
4. **Fund** each wallet with **10 ETH** from the notebook's pre-funded dev-genesis master wallet
5. **Register** both wallets as Authorities (admin signs)
6. **Authorize** a NAAN per authority (each wallet signs for itself)
7. **Create** ARK identifiers under each NAAN
8. **Resolve** and verify the stored ARK data

```bash
cd dARK_dapp/test
jupyter notebook test-dapp.ipynb
```

> **Note:** UUIDs and ARK names are generated with a Unix timestamp suffix (`authority-001-{ts}`), so the notebook is safe to re-run against the same blockchain state without conflicts.

## ARK Lifecycle (Summary)

```
1. Admin calls:      Authority.register_authority(uuid, wallet, encrypted_private_key)
2. Authority calls:  Authority.authorize_naan(naan)
3. Authority calls:  dARK.create_ark(naan, name, url, cid)
4. Anyone calls:     dARK.resolve(naan, name)  →  returns url
```
